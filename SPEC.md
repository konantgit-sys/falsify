# falsify — спека v1 (утверждена 24.11.2026)

Дата: 24.11.2026. Статус: **утверждена** 24.11.2026. Название — `falsify`. Лицензия — MIT. Публикация — сначала git-репозиторий, PyPI позже.

## 1. Что это и для кого

Инструмент, который проверяет подписанный журнал записей — и, главное, проверяет
**саму проверку**: умеет ли она падать там, где обязана.

Две вещи, которые он делает, и вторая — причина его существования:

1. `verify` — пересчитать хеш записи, проверить подпись Ed25519 над JCS-каноникой,
   проверить связь с предыдущей записью, напечатать вердикт по каждой проверке.
2. `mutants` — взять запись и испортить её девятью способами. Семь обязаны упасть
   (правка поля, подмена подписи, подмена хеша, `unix_tick` +1 с, смена `unix_tz`,
   подмена ключа, дробное число). Два обязаны **пройти**, и это не ошибка, а граница
   формата: `ts_human` +4 дня (метка лежит вне подписи, значит доказательством времени
   не является) и перестановка порядка ключей (каноника сортирует, значит форматирование
   не должно влиять). Инструмент печатает два счёта раздельно.

Для кого: для тех, кто строит собственные подписанные журналы (транспарентные логи,
аттестации поставки, журналы аудита агентов) и кому нужен не «зелёный свет», а
доказательство, что красный тоже возможен.

Отличие от готовых решений: подписанные журналы уже существуют (Sigstore/Rekor, in-toto,
SCITT) — там проверка есть, а **мутант-теста проверки нет**. Мы делаем не ещё один журнал,
а инструмент, который опровергает чужие и свои проверки.

## 2. Что входит в v1

- Python-пакет, одна внешняя зависимость — `cryptography`. Всё остальное stdlib.
- CLI: `vv verify FILE`, `vv mutants FILE`, `vv inspect FILE` (печать разобранной записи).
- Вывод: человекочитаемый по умолчанию, `--json` для машин.
- Код возврата: `0` — все проверки прошли, `1` — провал, `2` — файл не разобран.
- Библиотечный интерфейс: `from v2verify import verify, mutants`.
- Формат входа v1: наш canon (JSON-запись с `signature`, `record_sha256`, `timestamp`).

## 3. Чего в v1 нет (границы, чтобы не расползалось)

- Никакой сети: ни загрузки таблиц, ни HTTP, ни телеметрии.
- Никакого сервера и аккаунтов. Страница на поддомене — отдельный этап, не v1.
- Никакой поддержки чужих форматов (COSE, DSSE, JWS) — только наш canon.
- Никакого «угадывания» неизвестной версии каноники: неизвестно — значит FAIL.

## 4. Критерии готовности (проверяемые, не «на глаз»)

| № | Критерий | Чем проверяется |
|---|---|---|
| 1 | На всех доступных записях даёт те же хеши | эталон в `tests/golden.json`, сверка `record_sha256`. Факт на 24.11: файлов с подписью 4 (`fc78d8f7`, `d2764084`, `f2aa74a5`, `93b2d484`), ещё 2 клетки цепи лежат только в постах борды — подтянуть на этапе 1 |
| 2 | 7 мутантов FAIL, 2 мутанта PASS | `falsify mutants`: счётчики `7/7 упали` и `2/2 прошли`, `broken` пуст |
| 3 | Ставится в чистом venv без сети | `python -m venv`, `pip install --no-index -e .` |
| 4 | Работает без нашего репозитория | прогон в `/tmp` на скопированном файле записи |
| 5 | Ключ не нужен для проверки | `verify` не читает приватный ключ (проверка по grep + прогон от пользователя без доступа к нему) |
| 6 | Провал объясняется | на каждом мутанте печатается, какая проверка упала и почему |

## 5. Валидация

- `tests/golden.json` — 4 записи + их `record_sha256`: `fc78d8f7` (huilai, первая), `d2764084` (наша
  первая), `f2aa74a5` (huilai, пятая), `93b2d484` (наша шестая). Хеши сверены с таблицей huilai
  и с чужой реализацией независимо. Две оставшиеся клетки цепи — подтянуть на этапе 1.
- `selftest` — прогон «эталон проходит / 6 мутантов падают» встроен в CLI.
- Отдельно негативный тест: неизвестная `canonicalization_version` → FAIL, не «пропустить».

## 8. Серия B — пять тезисов (названия рабочие)

1. «Проверка, которая не умеет падать, — это не проверка, а оформление» — с 6 мутантами.
2. «Метка времени, лежащая вне хеша, доказывает ровно ничего» — опыт: +4 дня → PASS.
3. «Один эмодзи ломает хеш: UTF-16 против code point» — воспроизводится в 10 строк.
4. «Неизвестная версия — это FAIL, а не повод угадать» — и почему это ломает свежесть.
5. «Таблица, загруженная по отпечатку из той же записи, доказывает согласованность, а не подлинность» — с числами подделки 6160 → 6216.
